# Redisson 看门狗（Watchdog）MianShi知识点

> **用途**：分布式锁 / Redis 相关MianShi口述准备  
> **范围**：原理层 + 内部实现层；不绑定具体业务项目  
> **版本说明**：以 Redisson `RLock` / `RedissonLock` 主流实现为准，不同小版本类名可能微调，主干逻辑一致

---

## 一、值不值得准备

| MianShi层级 | 建议深度 |
|----------|----------|
| 初中级 | 原理：何时启用、30s/10s、与固定 TTL 对比、进程崩溃后多久释放 |
| 中级 | 加上：API 分支、`leaseTime=-1`、Hash + Lua、续期在客户端 |
| 高级 | 加上：`EXPIRATION_RENEWAL_MAP`、重入与定时任务复用、续期失败/GC/主从边界 |

**结论**：看门狗是 Redis 分布式锁里**高频且能拉开差距**的考点；「内部实现」在中级以上常作为追问，不必背每一行源码，但要能讲清**调用链 + 数据结构 + Lua 逻辑**。

---

## 二、30 秒总述（开场用）

> Redisson 在未指定锁租约（`leaseTime = -1`）时，加锁会给 Redis 里的锁 Key 设置默认约 **30 秒** 的过期时间，并在 **JVM 客户端**启动看门狗：大约每 **TTL 的 1/3**（默认约 10 秒）执行一次 Lua，若当前线程仍持有锁，就把整个 Key 的过期时间**重置为 30 秒**。业务线程正常 `unlock` 时删除 Key 并取消续期；进程崩溃则无人续期，最多约 30 秒后锁自动释放。看门狗解决的是「临界区执行时间不确定，又不想把 lease 设得特别大」的问题，**不**替代幂等、事务，也**不**解决主从异步复制丢锁等 CAP 问题。

## 三、原理层关键知识点

### 3.1 看门狗解决什么问题

| 痛点 | 看门狗做法 |
|------|------------|
| 固定 `EX 300s`：业务超过 300s 仍在跑，锁已过期 → 互斥失效 | 持锁期间周期性续期，业务可很长 |
| 为防过早过期把 lease 设很大：进程崩溃后锁占用很久 | 用较短 TTL（如 30s）+ 续期，崩溃后约 30s 释放 |
| 自研需自己写续期线程 + 停续期 + Lua | Redisson 内置调度与取消 |

**MianShi一句**：看门狗防的是**锁过早过期**，不是防业务死锁，也不是保证强一致。

---

### 3.2 何时启用 / 何时不启用

| API 形式 | 是否启用看门狗 |
|----------|----------------|
| `lock()` | 启用 |
| `tryLock(wait, unit)` **不传** lease | 启用 |
| `lock(10, TimeUnit.SECONDS)` | **不启用**（显式租约） |
| `tryLock(wait, lease, unit)` | **不启用** |

**判断依据（实现层）**：`leaseTime == -1` 才走看门狗；`leaseTime > 0` 与自研 `SET NX EX` 类似，到期自动释放。

**陷阱**：「用了 Redisson 就不用担心锁过期」——若调用了**带 lease 的重载**，看门狗**不会**启动。

---

### 3.3 默认时间与续期节奏

| 项 | 默认值 | 配置 |
|----|--------|------|
| 单次续期目标 TTL | 30 秒 | `Config.setLockWatchdogTimeout(ms)` |
| 调度间隔 | 约 **TTL / 3**（30s → 约 10s 一次） | 源码中 `internalLockLeaseTime / 3` |

**为何是 1/3**：留余量，避免一次 GC 或调度延迟导致 Key 已过期才被续上。

**观察现象**：`TTL` 可能从 30 降到 20 左右，再在续期时**一次性拉回 30**——说明续的是「满 TTL」，不是「在剩余时间上 +10s」。

---

### 3.4 续期发生在哪一侧

- **客户端**（Redisson 实例所在 JVM）的定时调度 + 异步回调  
- **不是** Redis Server 内置后台线程  

**口述**：「狗在应用进程里跑，Redis 只执行加锁/解锁/续期的 Lua。」

---

### 3.5 进程崩溃后多久可抢锁

- 约 **`lockWatchdogTimeout`**（默认 30s）  
- 与「自研 `EX 300`」对比：看门狗用短 TTL + 续期，**故障恢复更快**

---

### 3.6 与自研 `SET NX EX` 对比（表格背诵）

| 维度 | 自研 String 锁 | Redisson + 看门狗 |
|------|----------------|-------------------|
| Redis 结构 | String + token | Hash（field = 客户端标识:线程Id，value = 重入次数） |
| 租约 | 加锁时一次 `EX`，不续 | 默认 30s，周期性 `PEXPIRE` |
| 长临界区 | lease 估不准会失效 | 进程存活则续期 |
| 可重入 | 一般不支持 | 支持 |
| 解锁 | `GET==token` 再 `DEL`（宜 Lua） | `unlock` 内部 Lua + 校验线程 |

---

### 3.7 看门狗解决不了什么

1. **业务幂等、数据库事务**——锁只管互斥  
2. **续期失败**（长时间 STW、Redis 断连）——锁仍可能过期，其它实例可加锁  
3. **主从异步复制**——锁记录可能未同步到从库，主宕机后「锁丢失」——需 Redlock 或接受风险；与看门狗无关  
4. **误用 API**（显式 lease）——以为有看门狗实际没有

## 四、内部实现层关键知识点

### 4.1 加锁到启动看门狗（调用链）

```text
tryLock(wait, unit)     // leaseTime = -1
    → tryAcquireAsync / tryAcquireOnceAsync
    → 加锁 Lua：写 Hash field + 对 Key 设置 PEXPIRE（= lockWatchdogTimeout）
    → 加锁成功 → scheduleExpirationRenewal(threadId)
    → renewExpiration()：延迟 internalLockLeaseTime/3 后执行
    → renewExpirationAsync(threadId)
    → 成功则再次 renewExpiration()；失败则 cancelExpirationRenewal
unlock → 重入为 0 → 删 Key + cancelExpirationRenewal
```

**MianShi可点名三个方法**：`scheduleExpirationRenewal`、`renewExpiration`、`renewExpirationAsync`。

---

### 4.2 核心数据结构

#### `EXPIRATION_RENEWAL_MAP`

- 类型：`ConcurrentHashMap<String, ExpirationEntry>`（静态，**整 JVM 共享**）  
- Key：`getEntryName()`，一般为 **`{Redisson客户端UUID}:{锁名}`**  
- 作用：**同一把锁、同一线程重入**时，**不重复**创建多个看门狗定时任务  

#### `ExpirationEntry`

- 维护：持有该 entry 的 **threadId 集合**、当前绑定的 **Timeout**（定时任务句柄）  
- **首次加锁**：`putIfAbsent` 成功 → 调用 `renewExpiration()` 启动续期链  
- **重入加锁**：entry 已存在 → 只 `addThreadId`，**不再**起新狗  
- **重入释放**：`removeThreadId` 到 0 → `cancelExpirationRenewal`  

**MianShi一句**：「看门狗按锁条目复用，重入不会 N 个定时器同时续同一个 Key。」

---

### 4.3 定时调度（「守护线程」指什么）

- 实现：**连接管理器上的时间轮 / `newTimeout`**，不是每个锁 `new Thread()`  
- 模式：**链式调度**——每次 `renewExpirationAsync` 成功后在回调里**再次**调用 `renewExpiration()`，而非简单的 `scheduleAtFixedRate`  
- 首次延迟：`internalLockLeaseTime / 3`  

**纠正口语**：常说「看门狗线程」，准确说是 **客户端全局定时器 + 异步续期回调**。

---

### 4.4 续期 Lua（建议能口述）

```lua
-- KEYS[1]: 锁 Key（Hash）
-- ARGV[1]: internalLockLeaseTime（毫秒）
-- ARGV[2]: 当前线程在 Hash 中的 field（客户端UUID:threadId）

if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    redis.call('pexpire', KEYS[1], ARGV[1])
    return 1
end
return 0
```

**考点**：

1. 先 `hexists` 再 `pexpire` → **原子**，避免误续他人锁  
2. 过期的是 **整个 Hash Key**，Redis **不能**给 Hash 的单个 field 单独设 TTL  
3. 返回 `0` → 认为已不持有 → **停止**后续续期链  

---

### 4.5 `leaseTime` 分支（实现层）

```text
leaseTime > 0
    → 加锁 Lua 使用传入的 lease
    → 不调用 scheduleExpirationRenewal

leaseTime == -1
    → 加锁 Lua 使用 lockWatchdogTimeout 作为首次 PEXPIRE
    → 成功后 scheduleExpirationRenewal
```

---

### 4.6 unlock 如何停止看门狗

1. **Redis**：unlock Lua 将重入计数减 1，为 0 时 `del` Key  
2. **客户端**：`cancelExpirationRenewal(threadId)` → 从 Map 移除 entry、`timeout.cancel()`  
3. **异常**：续期失败（如 Redis 不可用）会 remove entry，续期链断开，依赖 Key 自然过期  

**考点**：`unlock` 须在**加锁成功的同一线程**（Redisson 用 threadId 校验）；线程池里 A 加锁 B 释放会失败。

---

### 4.7 实现层进阶 / 坑点

| 场景 | 说明 |
|------|------|
| Full GC / STW 过长 | 可能错过续期窗口 → 锁过期，其它实例可加锁 |
| Redis 断连 | `renewExpirationAsync` 失败 → 取消 renewal，不再续 |
| 多把锁同线程 | 每把锁一个 `entryName`，各有一条续期链，不是「每线程一个全局狗」 |
| 与 Redlock | 看门狗只延长**当前 Redis 节点**上的租约；多节点一致性是另一套方案 |

## 五、场景题与参考答法

### Q1：扣库存要 2 分钟，锁 `EX 10` 会怎样？

**答**：10 秒后 Key 过期，其它线程可加锁，会出现两个线程同时改库存 → 超卖。若用 Redisson 看门狗（不传 lease），会每约 10s 把 TTL 续回 30s；若用 `lock(10, SECONDS)` 则**没有**看门狗，同样会挂。

---

### Q2：看门狗是不是就不会死锁了？

**答**：不是。看门狗只防止**锁因 TTL 过早失效**；若业务逻辑互相等待，锁会一直续期占着。应配合 `tryLock` 超时、避免嵌套锁顺序不一致等。

---

### Q3：为什么不用 `EX 300` 代替看门狗？

**答**：可以，但进程崩溃后锁要等满 300s 才释放。看门狗用短 TTL + 存活续期，**正常时**不怕长业务，**异常时**约 30s 可恢复。

---

### Q4：续期在 Redis 还是 Java？

**答**：**调度在 Java**（Redisson 客户端定时器），**生效在 Redis**（Lua 里 `pexpire`）。Redis 不会自己帮你看门狗。

---

### Q5：重入时看门狗起几个？

**答**：同一线程对同一把锁重入，**共用一个** `ExpirationEntry` 和一条续期链；重入计数在 Hash 的 value 里，续期仍针对整个 Key。

## 六、与 ZooKeeper / etcd 锁（点到为止）

| 对比 | Redis + Redisson | ZK / etcd |
|------|------------------|-----------|
| 一致性 | 依赖单 Redis 或 Redlock 争议 | 强一致、临时顺序节点 |
| 性能 | 高 | 相对较低 |
| 续期 | 客户端看门狗 + TTL | 会话保活 / lease |

**MianShi一句**：「要极简高性能用 Redis；要强一致、公平排队可提 ZK，但大多数业务MianShi Redisson 足够。」

## 七、分层背诵清单

### 初中级（必背）

- [ ] 未指定 lease 才启用；显式 lease 不启用  
- [ ] 默认 30s TTL，约每 10s 续一次（1/3 间隔）  
- [ ] 续期在**客户端**，Redis 执行 Lua `pexpire`  
- [ ] 崩溃约 30s 后释放；比超大 `EX` 恢复快  
- [ ] 对比自研 `SET NX EX` 的一张表  

### 中级（建议背）

- [ ] `scheduleExpirationRenewal` → `renewExpiration` → `renewExpirationAsync` 链  
- [ ] `EXPIRATION_RENEWAL_MAP` + `ExpirationEntry` 与重入复用  
- [ ] 续期 Lua：`hexists` + `pexpire`  
- [ ] `unlock` 同线程、`cancelExpirationRenewal`  

### 高级（选背）

- [ ] 链式调度 vs 固定周期  
- [ ] GC / 断连导致续期失败  
- [ ] 主从异步复制与 Redlock 边界

## 八、附录：自研锁 vs Redisson 解锁 Lua 对照（口述用）

**自研 String 锁解锁（常见写法）**：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**Redisson 续期（看门狗）**——见 §4.4；**解锁**由 Redisson 内部另一段 Lua 处理重入计数与 `del`，应用层只调 `unlock()`。
